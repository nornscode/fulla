# Architecture

## Process model

In production, one Fly app and one process, asleep between requests. The HTTP server (`server.py`) answers three callers: Norns's wake for the worker half, Norns's run webhook for the channel half, and the messenger's inbound: Telegram's webhook, or the Signal forwarder's signed POSTs to `/signal`. The worker incarnation loop (`wake.py`) runs in the main thread and is driven by wake requests, each held open while the worker serves. Norns is the only process that runs all day.

Locally, `fulla` runs the worker all the time and polls the messenger (Telegram's getUpdates, or signal-cli's receive stream); run events still arrive over HTTP from the local Norns, so there is one outbound path in both shapes.

The volume holds `facts.json`, `directives.json`, `soul.md` (who Fulla is, a page it writes with the owner; see `soul.py`), `calendars.json`, `feedback.json`, `gaps.json` (capabilities the owner asked for that it lacks), the reminder index, and `channel.json` (messages named by address and id, so both messengers share it): what the channel has posted (so a duplicate delivery or a reconcile never repeats a question), what it has relayed, and the owner's messages Norns refused as busy, still to send.

## The Mac worker

A third process, on the owner's Mac, when they want one: `fulla-mac` joins Norns with capabilities `["tools"]` and no agent definitions, and serves the `mac_*` tools (Things, Apple Reminders, iMessage, notifications, window arrangement, home shortcuts, allowlisted AppleScript). Norns dispatches a tool call by name to whichever connected worker holds it, so the manager's allowlist can name tools the Fly worker never serves or declares; they are offered exactly while the Mac is connected and absent when it is not, and the prompt tells the manager what absence means. Side-effecting calls carry Norns's idempotency key, so a call re-dispatched after the Mac's connection dropped is not run twice.

The restriction is config on the Mac, not prompt: which apps AppleScript may address, who iMessage may go to, which tmux sessions may be read and typed into, and which Shortcuts folder holds the home automations. All are short lists; the iMessage and tmux lists are empty by default. The home has no scripting dictionary, so it is reached through Shortcuts: `mac_home_run` runs a shortcut only if it is in that one folder, and the owner edits the folder, not the code, to change what Fulla may do in the house.

## Confirm cards and iMessage

Some actions happen only when the owner approves them in the chat. `confirm.py` is the mechanism, in the channel: `Channel.propose(kind, payload)` posts a card (plain text, shown verbatim) with Send, Edit and Cancel, and records it in `channel.json` with the payload's sha256 digest. Each button carries the card id and the first eight characters of that digest, so a tap on a card that has since been edited does nothing, and each step (approve, edit, cancel) moves the confirmation once, under the channel's lock, saved before anything acts. Edit takes the owner's next message (or a reply to the card) as the new text and posts a fresh card with a new digest. On Signal the card is the same text with a "Reply to this with one of: Send · Edit · Cancel" line: a quoted reply naming a label, or a cancel reaction, on the current card builds the same callback data from the card as it stands and goes through the same tap handler, so it is one-shot and pinned alike; a reply to a card an edit retired is refused, and any other quoted reply to an undecided card is new text for it. A 👍 never sends: it is too easy to leave by accident, so it gets a pointer to Send instead. The same reply or reaction works on Telegram. The card goes where the owner is talking to the manager right then (the address of their run in flight), or to the primary address when nobody is, and it remembers that address. Only the owner decides it, one to one, at that address: a friend's or group member's button, quoted reply or reaction never reaches the card code (the channel routes them to `fulla-social`), the owner in a group is social too, and the card code checks sender and chat again rather than trusting the quoted message id. Cancel words (#43) give way to cards: a cancel word quoted on a card is that card's Cancel, never a cancel of some run; while an edit waits, an unquoted cancel word stops the run in flight at that address if there is one and otherwise drops the edit, and is never taken as the new text. A `ConfirmKind` says how to render a payload, how to apply an edit, and what approving does: start a Norns run, whose outcome is written back onto the card, or finish at once.

An iMessage is the first kind. The manager's `draft_imessage(to, text, why)` checks the recipient against the allow list the Mac announced with itself (`hosts.json`) and proposes a card headed with the name and handle; it sends nothing. Send starts a `fulla-mac-task` run carrying only the card's id and digest, so the Mac being off is the usual queue: the run parks on "Waiting for the Mac." until the nudge. On the Mac, `mac_imessage_deliver(draft_id, digest)` claims the payload from Fly (`POST /confirm/claim`, signed with the Norns API key like `/hosts`); Fly hands it out only if the owner approved exactly that digest and nobody claimed it yet, and the Mac re-checks the digest and the handle before sending. So a model can carry the id but never choose the text, and a replay sends nothing. The manager never holds `mac_imessage_deliver`, and `mac_applescript` refuses Messages whatever `FULLA_MAC_APPS` says. Cancel works until the Mac has claimed it.

Reading is separate from sending. `mac_imessage_recent` and `mac_imessage_unanswered` read `chat.db`, and name its handles from the Contacts store (`AddressBook-v22.abcddb`, the root one and each source's), both under the one Full Disk Access grant; the allow list's names come first, then Contacts, kept ten minutes. A name read there changes nothing about who may be sent to: `resolve_recipient` still reads only the allow list.

## Host workers

The tmux tools (`tmux.py`) and the shell tools (`shell.py`) are platform-neutral, and any other machine of the owner's can serve them: `fulla-host` (`host.py`) is the same tools-only worker with only those tools, under the machine's own name from `FULLA_HOST`, so a Linux box called `box` serves `box_tmux_list`, `box_tmux_read` and `box_tmux_send` as the worker `fulla-box`. Names matter because Norns dispatches a tool call by name to one worker; two machines serving `tmux_read` would be a coin toss. The Mac is always a host, named `mac`, and serves its tmux tools alongside the Apple ones.

Fulla's memory of machines is `hosts.json` (`hosts.py`). A machine worker announces itself when it starts: a POST to `/hosts` on the Fly app, signed Stripe-style with the Norns API key, which both ends already hold. The channel registers it and, when it is new or its allowed sessions changed, pushes the manager's definition to Norns over REST: the prompt re-rendered (its Machines section lists every machine by prefix, platform and sessions) and the allowlist re-built with every known machine's tools. The same push serves directive and soul changes; the prompt is still rendered one way, `worker.manager_prompt`. The worker also builds its agent definitions fresh for each incarnation, because the SDK upserts them on every join: a definition built once at process start would put a stale prompt back on the server at the next wake. The per-turn note reads the registry each turn and says, for the Mac and for each machine, whether its tools are in the list. So the manager has a memory of every machine, routes by prefix, and knows from the note which are up. Nothing about machines is configured on Fly; Fly's machine wakes briefly for an announcement, as for any request, and workers announce only on start.

`<host>_tmux_send` and `<host>_exec` are the two tools that run commands, which `mac_applescript` is forbidden to do. `<host>_exec` and the file tools (`<host>_read_file`, `_write_file`, `_edit_file`, `_grep`, `_glob`) are on only with `FULLA_SHELL=1` on that machine and refuse otherwise; on, they run as the worker's own user, a command in its own process group killed past its timeout, output capped, the Norns key kept out of the environment. For tmux,  The guard is the session allowlist, checked against the session tmux resolves the target to, plus the prompt's rule to type only what the owner asked for. Text, targets and session names reach tmux as argv, never through a shell. `<host>_tmux_new` and `<host>_tmux_rename` are guarded by the same list: a new name must be on it, and a rename needs both the old session and the new name on it. `<host>_tmux_new` takes no start command, because tmux runs a one-word command through the default shell; a new session starts its shell and `send` stays the one way in. Captures keep their dimmed (SGR 2) runs marked as «…» and drop every other escape, so a placeholder is not read as typed input.

## Two agents

**fulla** is the manager. one standing conversation keyed `config.conversation_key`: `telegram:<user id>` or `signal:<owner number>`, built once and shared with the follow-up tool. It has `now`, the facts tools, and the reminder tools. It never calls `wait`.

**fulla-reminder** is one commitment. one run per reminder, started by the manager's `schedule_reminder` tool through the REST API with a unique conversation key. Its life: `now`, `wait` until due, `ask_human`, then finish with `Done:` or `Dropped:`. Snooze is `wait` and ask again.

**fulla-followup** is one of Fulla's own check-backs, started by `schedule_followup` like a reminder and indexed in `followups.json`. Its life: `now`, `wait` until due, `deliver_followup`, finish. `deliver_followup` is the only tool that writes into the standing conversation: it sends `[scheduled] follow-up: <what>` to `fulla` under the same key, once (the index records delivery, so a re-dispatched or repeated call posts nothing), and reports Busy on a 409 so the run waits a minute and tries again rather than landing in the middle of a turn. The channel does not know this agent, so nothing of the run reaches the owner; the manager's turn it starts is relayed like any scheduled one. It never calls `ask_human`.

**fulla-watch** is a follow-up with no due time, for a coding sandbox. The manager's `watch_environment(what, environment_id, job_id)` starts it and indexes it in `followups.json` like any follow-up (`list_followups` and `drop_followup` see it). On the light model, it polls `get_coding_task` every four minutes while a job is queued or running, or `get_environment` while the environment is provisioning or its pull request is pending, then `deliver_followup` with the state it saw: `[scheduled] follow-up: <what>` plus `(watched: <id> is <state>)`, the state cut to two plain words so nothing the coding agent wrote reaches the manager through it. After forty checks it delivers "still running". It replaces a manager follow-up every five minutes per job, each a full turn of the manager's, which was about half the manager's tokens on 2026-11-16. Bubbo's tools are allowlisted on it by name, and `coding.CodingGuard` lets it call only those two reads, on what the manager may drive, and claims nothing from its history.

**fulla-reader** reads the web. a fresh conversation per launch, tools `now`, `web_search` and `fetch_url` and nothing else. The manager launches it with Norns's built-in `launch_agent`, its one allowlisted sub-agent, and gets the reader's answer back as the tool result. The split is for prompt injection: a page can say anything, and the manager can type into a shell and draft iMessages, so the run that reads pages has nothing side-effecting to call and the manager only sees an answer. While the reader works the manager's run is `running`, not `waiting`, so a message from the owner meanwhile joins the run after the reader's answer, never taken as an answer. The child's run is not relayed; its answer arrives through the manager's reply. If the reader fails or is cancelled, Norns hands the manager a `subagent_failed` result, so the manager's turn ends either way.

Norns offers its built-ins (`wait`, `ask_human`, `launch_agent`, `list_agents`) to every agent, and no allowlist removes them, so the prompts' "never call `ask_human`" is enforced twice. The worker drops them from the reader's LLM calls (all four) and a follow-up's (all but `wait`), recognising the agent by the `agent_id` core puts on each task (`wake.WITHHELD`). And if either agent asks anyway, the channel answers the `run.waiting` at once with "Nobody can answer questions here. Finish now with what you have.", posts nothing, and records the ask in `channel.json` so a redelivery is not answered twice; reconcile does the same for one found waiting on a cold start. Otherwise a reader parked on a question would hold the manager's turn, and every owner message behind it, forever.

Why two: a run parked on `ask_human` treats the next message to its conversation as the answer. If the manager were asleep on a reminder, the owner's next unrelated message would wake it as a reply. So the thing that chats and the thing that sleeps are different runs.

## Message flow

```
owner types text ──► messenger inbound ──► channel._chat ──► send_message(fulla, key)
                                                               (no wait; answered 200)
                                          ──► post "Working…" + Cancel; typing re-sent
                                              every few seconds until the run's event
                       a run under way ──► sent with `interject`: Norns adds it to that run
                                            before its next model call (or starts the next
                                            run with it, if the run ends first); one reply
                               409 busy ──► (an older Norns) keep it in channel.json `pending`;
                                            say once that it's queued behind the current run

Norns run webhook ──► /norns/events          (each takes the run's Working… down first)
   run.waiting   ──► post question + buttons (deduped by run_id:tool_call_id)
   run.completed ──► relay output unless "[silent]" (deduped by run_id)
   run.failed    ──► post a pointer to the run
   (a manager run completed or failed ──► send everything pending, joined, in order)

manager's send_message tool, mid-turn ──► Channel.say: to where the run answers, at once
                                          (deduped by run_id:digest of the text)

owner taps button / replies to question ──► client.reply(run_id, answer)
                                          ──► edit the question message with the answer
                                          ──► a manager run shows Working… again

owner reacts to a question ──► the button's answer, if the emoji means one
owner reacts to another of ours ──► send_message(fulla, '[reaction] 👍 on your message: "…"'),
                                    no Working…; deduped by message_id:emoji:date
manager reply is one allowed emoji ──► setMessageReaction on the owner's message

owner taps Cancel ──► POST /runs/:id/cancel ──► edit to "Cancelled."; the run's later
                                                events are not relayed

cold start ──► reconcile: GET /runs, post any waiting question not yet posted,
               take down Working… for runs that ended while asleep, send pending
```

Pending messages are new chat, never an answer: while the standing
conversation is parked on a question they stay put, because Norns would read
the next message as the answer. A plain message typed while parked still goes
straight through and is the answer, as before. A send that is busy again
leaves them pending for the next run's end; nothing polls.

Working… is posted for manager runs the owner set going, not for reminders
(a snoozed reminder is waiting, not working) or scheduled runs. A run whose
event beats its Working… message gets none. The typing indicator is a thread
per run that stops with the message or after ten minutes.

Buttons carry `a:<run_id>:<answer>` as callback data. A reminder's buttons are Done, Snooze 1h, Snooze 1d, Drop; anything else gets Yes and No. A free-text reply to the question message is also an answer. On Signal there are no buttons: the labels go out as a "Reply to this with one of" line under the question, a quoted reply or a reaction answers, and a reply saying "cancel" (or a ❌ reaction) on the Working… message is the Cancel button. Only runs of `fulla` and `fulla-reminder` are relayed; the webhook fires for every run in the tenant.

## Scheduled runs and silence

Four triggers run in the standing conversation: the morning brief, a check-in every two hours during the day, a nightly review at midnight that writes the day's durable details to facts, and a shipping check after it that reads Fulla's own repository's commits (when it is among the owner's sources) and notes which open gaps and feedback items look shipped, for the brief to ask about. All are ordinary messages prefixed `[scheduled]`. The triggers are Fulla's own to make: the manager's `list_triggers`, `set_trigger` and `drop_trigger` (`tools/schedule.py`) manage them in Norns with the key it holds, always on the manager and the standing conversation, from local times the owner says (`schedule.cron_for`); nothing at start or in CI touches them, and the owner may put any message of their own on a timer the same way. A scheduled run may not call `ask_human`, because the manager's conversation would park and the owner's next chat message would be taken as the answer. That is enforced like the reader's: on a turn whose newest user message begins `[scheduled]` (a timer's, or a follow-up's delivery) the worker leaves `ask_human` out of the manager's LLM calls (`wake.WITHHELD_ON_SCHEDULED`), and if a run Norns says a timer started (`trigger_type: "schedule"` on the event) parks anyway, the channel answers it at once and posts nothing. A check-in with nothing to say ends with `[silent]`; the channel drops that output but the run stays in the log. The manager may also send the owner messages mid-turn with `send_message` (one per tmux session, say), delivered at once by `Channel.say` to the address the run answers, the primary one for a scheduled turn; a final `[silent]` drops only the final reply, not what was already sent. The turns that are never delivered, the nightly review and the shipping check, are not offered it (`wake.WITHHELD_ON_QUIET`); the brief, a check-in, a question and a follow-up keep it, since they are meant to reach the owner when they have something to say.

## Signal and SMS

A messenger is a `transport.Transport`; the channel calls six things on it (send, edit, delete, typing, react, acknowledge a button) and reads one `Inbound` shape, which says which transport it came in on. `telegram.py` is one, `signal.py` another, `sms.py` the third, and the channel holds any of them at once by name. It thinks in addresses, `telegram:<chat>`, `signal:<number>` or `sms:<number>`: each run the owner starts remembers its origin address (`origins` in the state file) and is answered, questioned and shown as Working… there; a run with no origin (a scheduled turn, a reminder) goes to the primary address, `channel.primary`. All the owner's addresses share the one standing conversation, so Fulla has one memory of them whichever app they pick up. Messages are named by address and id together, since a Telegram id and a Signal timestamp can be the same number.

signal-cli cannot live in the Fulla app: it is a JVM that must stay connected, and the app sleeps. So it is a second Fly app, `fulla-signal` (`deploy/signal/`): the signal-cli-rest-api image in json-rpc mode, one machine always on, a volume for the account's keys, no public service. Fulla sends by calling it over the private network. Upstream's s6 init cannot run there (it insists on PID 1, which Fly's own init holds), so `run.py` is the entrypoint: it starts upstream's two processes and the forwarder, and restarts what dies. Inbound is its websocket, which the forwarder in the same container (`forward.py`) holds open, POSTing each data message to `https://fulla.fly.dev/signal` with an `X-Norns-Signature` made from a secret derived from the webhook's (`signature.signal_secret_token`). A POST starts Fulla's machine like any other request. Receipts and typing are not forwarded; each would wake it.

Signal's servers hand a message over once, so the forwarder must not lose it. Each envelope is written to a spool directory on the volume before anything else, and a delivery thread sends the spool oldest first, retrying the head until Fulla answers 2xx: a cold machine (several seconds), a deploy, or a wrong secret all just mean the message waits on disk, in order. The guarantee carries through Fulla's door. The channel calls a message handled only once it is safe: Norns has it, or it sits in `pending` in the state file. If Norns cannot be reached, `handle` raises `NotTaken` and the server answers 503, so the forwarder (or Telegram, which retries for a day) brings the message again; a redelivery of a message already kept in `pending` is used as the retry timer for the flush. A reply lost on the way back means the same message arrives twice, so the channel remembers the ids it has handled (`handled` in its state file) and ignores a redelivery once Norns has it.

A message is named by its timestamp, which is what the channel's state keys on. Edits re-send with `edit_timestamp`; take-downs are remote deletes; the typing indicator lasts fifteen seconds and is re-sent. Fulla may react with any single emoji, not Telegram's fixed list. Only the configured owner (number, Signal account id, or both) is heard; groups are never read, since Fulla never acts in public.

SMS is Twilio (`sms.py`), and needs no machine of its own: Twilio holds the number (the Signal number, if that is a Twilio number; Signal used it once and texts to it land at Twilio) and POSTs each incoming text to `/sms` as a form signed with the account's auth token over the URL and the sorted fields (`sms.verify_signature`); `Sms.set_webhook` points the number there on start, and points its fallback there too, because Twilio gives a webhook fifteen seconds and otherwise never retries, so the fallback is the one second try a cold machine or an unreachable Norns gets. The route answers empty TwiML, since a 200 Twilio cannot parse is an error in its console. Outbound is the Messages API, one call per 1600 characters, split at paragraphs; a message is named by its SID, a string, which the channel's refs carry as they carry any id. The transport does nothing for what a text cannot do (edit, delete, typing, reactions) rather than the channel branching on it; the one rule the channel has for it is shared with Signal, since both lack buttons: an unquoted message that is exactly a label of an open question at that address, or of the one open card there, is that button (`_answer_by_label`), because SMS has no quoting at all. Markdown is flattened (`sms.render`) and the few typographic characters that would push a message out of GSM-7 are swapped for ASCII, since one of them halves every segment. Local dev has no inbound stream, so `poll` lists the number's messages every few seconds. SMS carries the owner's chat with the manager only: there are no groups, and the people list is not consulted for it beyond what the channel does for every messenger.

## Friends and groups

The channel admits a message in one of three ways (`Channel._admit`). The owner, one to one, is the manager and the standing conversation, as always. A person on the owner's list (`people.py`), one to one, is the social agent `fulla-social` in a conversation keyed `social:<address>`. In a group, the group must be on the list and allowed, the sender must be listed (the owner counts), and the message must address Fulla by name, by bot handle, or by a reply to it; then it is the social agent in `social:<group address>`, and the owner's own words there go to it too, because the group can read the answer. Everything else is dropped at the door, logged, never answered.

A group gets onto the list by the owner speaking in it with Fulla present: the channel remembers the group, asks the owner once at the primary address (Yes and No buttons, or a reply saying yes or no), and records the answer. A person gets onto it the same way when they address Fulla in an allowed group without being listed: remembered with the name and id the messenger gave, asked about once, allowed or ignored by the answer. A person may carry several ids per messenger, since Signal shows an account id and only sometimes the number. The social agent's wall is its tool list, `now` and the reader through `launch_agent`, and nothing in its prompt from the owner's side: no soul, no directives. A non-owner's text reaches it inside the untrusted marker. A group message that addresses it comes with the thread before it: the channel keeps every text said in an allowed group, Fulla's own replies and reminders too, in `group_ring` in the state file (`channel.group_context` messages per group, none older than two hours), and `_handle_social` prepends them as one untrusted block, the owner's lines labelled but inside it, since the owner's words are instructions only when they address it. The thread goes with the first message a run gets, whether it starts the run or waits for one; a message queued behind one already waiting goes without, and the next turn's thread covers the gap. Unaddressed messages are still never answered, and a group the owner has not allowed stores nothing. It never asks a question (an `ask_human` from it is unstuck like the reader's), and it never sleeps: `wait` is withheld from its LLM calls, because a sleeping run would hold the chat's conversation busy and queue everyone's next message behind it; a timed thing is `schedule_group_reminder`, a run of `fulla-group-reminder` that the channel posts back into the chat when it ends, found through the run that scheduled it (`runctx` carries the run id into the tool; `social_origins` in the state file remembers where that run's answers went). The post tags the person who asked: the channel records who wrote each message a social run answers (`speakers`, every speaker of a bundle, in order), lends that lookup to `runctx.current_speakers`, and the tool stores the asker in the reminder's index entry, the one speaker when there was one, or the one the model names in `asked_by` out of those the channel heard: the run's speakers first, then the group's members from the people store, found through `runctx.current_address`, never anyone else. The id used for a member is the account id when Signal has shown one, else the number. The channel then writes "⏰ @Dana: stretch" and passes `mentions` to the transport, which makes the messenger's own tag of it (Signal a mention range in UTF-16 units, Telegram a `tg://user` link). Everyone who speaks in an allowed group becomes one of its members in `people.json` (`saw_in_group`), a Person with an id of Fulla's own, so that people can be told apart and found by name later. If a run sleeps anyway, the next message finds the chat busy, sees the run's newest event is `waiting_for_timer`, and cancels it; the failure flushes what was waiting. Its replies are plain text, never reactions, and a failed run is logged, not announced in the group. Each social address has a daily cap of answers (`social_counts` in the state file), told once when reached. Messages that arrive while a run is in flight for that address wait in `social_pending` and go together when it ends. The owner can start one of these conversations over from their own chat with `/reset <group or person>` (`_reset_social`): the run in flight there is cancelled, the social conversation deleted in Norns, and what was queued and the group's thread dropped; the people list, their reminders and the day's count stay. It exists because a wrong answer of Fulla's in a group ("I can't set that") sits in that conversation's history, and no prompt line reliably argues the model out of its own history.

Each allowed group has a directory of its own, `data/groups/<id>/` (`groups.py`, `GroupStore`), named by a short random id because an address can change. The people store stays the door; the directory holds what the group has: `group.json` with its address, name, members, admin, the tools the owner enabled from the fixed catalogue, its sources in Mimir's shape (`type`, `identifier`, `label`), project and cap; `facts.json`, written only through the injection screen (`injection.py`, borrowed from Mimir: instruction-override phrases, concealment, chat-template tokens, invisible characters); `reminders.json`, that group's reminders (`tools/group_reminders.py` writes there when the run is a group's, found through `runctx.current_address`, which the channel lends from `social_origins`; a friend's one-to-one reminders stay in the shared `group_reminders.json`, and `known` looks in all of them); and `credentials.json`, each value encrypted with a Fernet key derived from `FULLA_SECRET`. The channel calls `GroupStore.sync` when a group is allowed and when someone speaks in one, so a directory appears when the door opens and its members follow the people store; a dropped group keeps its directory. The owner's tools over all this are the manager's alone (`tools/groups.py`), so only the owner, in their own chat, changes a group's tools, sources or credentials; a credential never comes back out, and the hard limits say so. What a group may do is held by two locks. The outer one is Norns's allowlist, drawn per group: `worker.group_agent` declares one agent per allowed group, `fulla-group-<id>`, whose `allowed_tools` is exactly the social set (`now`, `group_sources`, the group reminders) plus what the owner enabled from the catalogue (`tools.GROUP_TOOL_SETS`: "memory", "github" and "linear"; "web" is the reader, allowed as a sub-agent only for a group that has it), and whose prompt is rendered from the group's record alone: its name, project and sources by label, nothing about any other group, nothing of the owner's, and nothing of Fulla's own. The definitions are built from the store at every join (`main._setup` hands the incarnation loop a builder that syncs the directories first) and pushed over REST when the owner changes a group or allows one (`main.push_groups`, through the SDK's own upsert, the way the manager's prompt is pushed when a directive changes); the channel sends a group's messages to its agent (`Channel._agent_for`), falling back to `fulla-social` only while the agent is not on the server yet, recognises a group agent's runs by its name's prefix, and `/reset` clears both. A listed friend one to one keeps `fulla-social`, now the same prompt with no group and no sources. The inner lock is the tool itself, bound to the run: `groupctx.current()` resolves the group from `runctx.current_address`, which the channel lends from `social_origins`; a group tool refuses with a fixed sentence when there is no group in context, and `groupctx.scoped` refuses any repository, team or host that is not among the group's sources even when the model names one, working on the group's own sources when none is named, never on "all". Tool errors to a group are fixed sentences, never exceptions, paths, hosts or URLs of Fulla's own. The group agents are withheld what the social agent is (`wake.withheld_for`). Tests hold that Group A cannot name Group B's repository with or without the allowlist widened, that a tool with no run in context refuses, and that the owner's prompt and stores never appear in a group agent's prompt or tool list.

The group tools themselves come from Mimir and PR #39, with scope moved from the argument to the run. `norns_app/github.py` is the shared part: a REST client over httpx (no SDK, the app is small) that takes a token and knows no allowlist; it is meant to be extracted when Mimir takes it too. `tools/group_github.py` binds it: each tool resolves its group, takes the token from `GroupStore.credential`, resolves repositories through `groupctx.scoped` (the one named, by identifier or label, or all of the group's with none named), wraps titles, bodies, comments, commit messages and file contents in the untrusted marker, and turns every failure into a fixed sentence ("This group has no GitHub token yet", "GitHub said 404.", "GitHub didn't answer that."). The reads are pull requests with CI and reviews, one pull request with its description and comments, issues, one issue, commits, a file or directory with paging, and search. The writes are cards: `propose_merge`, `propose_issue` and `propose_review` post a `github_cards` kind to the owner's own chat through `Channel.propose`, with the group's id and name in the payload; the owner's tap (or a quoted reply saying Merge, File or Post on Signal) acts with that group's token, a merge of exactly the head sha the card showed, a review (COMMENT, APPROVE or REQUEST_CHANGES, with the whole body and any line comments on the card, Edit replacing the body) on that head, and the group only ever hears that the owner was asked. `tools/group_memory.py` is `group_remember` and `group_recall` over the group's `facts.json`, through `injection.scan` on the way in and inside the untrusted marker on the way out; the group prompt carries a count and the newest few facts as its status. Linear is the second source kind, in the same shape: `norns_app/linear.py` is a GraphQL client over httpx that takes a key and knows no allowlist; `tools/group_linear.py` reads issues in the group's teams (`linear_team`, by key) and projects (`linear_project`, by id or slug), one issue by identifier, and proposes a new one as a `linear_cards` card the owner files with the group's key. An issue the key can reach but the group's sources do not hold is refused after the fetch with the same sentence as before it, so a wider key is not a wider group. Writes are split by reversibility. A merge touches code and cannot be undone, so it stays a card; an edit to a Linear issue is visible in its history and reversible, and is bounded twice already, by the group's sources and by the key the owner gave it, so the owner may let a group do those at once: the catalogue entry `linear_edit` (which implies `linear`) puts `linear_assign`, `linear_update` (state, priority, title, labels), `linear_comment` and `linear_create_issue` on that group's allowlist. Each fetches the issue and applies `_mine` before it writes, resolves an assignee, a state or a label by name against what Linear holds for that team (one exact match, or a question naming the candidates) rather than taking an id from the model, and does nothing that deletes or archives; `_editable` refuses from inside a group without the switch, so the tool and the allowlist agree. The owner's own directory needs no switch, and the manager holds the edit tools always. The social agent is given every group tool to serve (so an incarnation can answer a group's calls and the serverless declaration lists them) while its allowlist stays the social set. The catalogue's `coding` entry is the one whose tools Fulla does not serve: Bubbo's coding tools (`provision_environment`, `get_environment`, `start_coding_agent`, `get_coding_task`, `cancel_coding_task`, `destroy_environment`, `open_pull_request`) go on the group's allowlist by name, as on the manager's, and Norns routes them to the Bubbo worker. With no tool of Fulla's in front of them, `groupctx` cannot refuse from inside, so the inner lock moves to where Fulla does stand: it serves every LLM call of the manager and the groups, and `wake.ServingNorns` hands each response to `coding.CodingGuard.check` before Norns sees the calls. The scope is the agent core named on the task (the manager is the owner, `fulla-group-<id>` is that group, anything else is nothing). A group's provision must name one of its `github_repo` sources and goes out as that source's identifier; a sandbox or job belongs to the scope whose provision or start created it, read from the tool result in that agent's own history into `data/sandboxes.json`, first claim wins; a group drives only its own, the manager anything no group holds. A call that may not go turns the whole step into a fixed sentence as the run's answer. A group cannot wait, so it polls a job with `schedule_group_followup`: a `fulla-group-reminder` run indexed with `followup`, whose end the channel answers by sending "[scheduled] follow-up you set: …" into the group's own conversation instead of posting a line, counted against the chat's daily cap so a job polled forever stops with the day's turns.

The owner's own sources go through the same door. `data/groups/owner/` is a directory of the same shape (`GroupStore.owner`), named "me" to the manager's group tools, left out of `all()` so no agent is built for it and no address routes to it. The manager holds the groups' `github_` and `linear_` tools; `groupctx.current` resolves the owner's directory only when the calling run is the manager's, which it learns from the agent id core puts on every tool task (`wake.ServingNorns._is_manager`, resolved once per incarnation from the server, lent through `runctx.current_is_manager`), never from a model argument. A group's run resolves to its group or to nothing. The manager's prompt renders what is connected for the owner ("Your sources"), and a change to any directory pushes both the groups' agents and the manager's prompt.

## What's deliberately not here yet

- Cancel on a Norns without `POST /api/v1/runs/:id/cancel`. The route is
  nornscode/norns#46; on an older Norns the Cancel button answers that Norns
  wouldn't cancel the run.

- A nudge when a question goes unanswered. `ask_human` parks indefinitely and has no timeout; adding one to Norns is the planned fix, not a loop in the worker.
- A relay for a completion missed while asleep. Reconcile covers questions, which stay visible as `waiting`; a missed `run.completed` is gone. Norns has no delivery log yet.
- Email. Calendar is in (read-only iCal feeds); email waits until the loop has earned trust.
- Structured asks. Questions are strings and answers are strings. The channel maps buttons onto that; typed asks are a Norns change.
