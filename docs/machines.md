# Your terminals and machines

Fulla can look at your tmux sessions, type into them, and start or rename them: "what's the test run in my work session doing?", "type `make deploy` into the shell window on the box", "start a session called scratch in ~/proj". On the Mac this rides on the Mac worker; on any other machine, a Linux box say, a third tools-only worker, `fulla-host`, serves the same tools under that machine's name, so `FULLA_HOST=box` serves `box_tmux_list`, `box_tmux_read`, `box_tmux_send`, `box_tmux_new` and `box_tmux_rename`. A new session starts with its shell; there is no start command, since tmux would run it through the shell, and typing into it is how anything runs. Text that is dimmed on screen, like the placeholder in Claude Code's input box, reaches it marked as «…», so Fulla does not take it for something typed.

Fulla remembers every machine it has met. A worker announces itself to the Fly app when it starts (`FULLA_URL` on the machine, signed with the Norns key), and Fulla writes it into `hosts.json`: the name, the platform, which sessions it allows. From that memory come the machines it may call, the list of them in its prompt, and a note on every turn saying which are connected right now, so it routes "the box" to `box_tmux_read` and tells you when the box is off. Nothing to configure on Fly: start the worker once and Fulla knows it.

Typing into a shell runs commands, so this is off until you allow it. On each machine, `FULLA_TMUX_SESSIONS` names the sessions it may read, type into, create and rename to (`*` for all of them); it sees nothing else, and the check is on the session a target resolves to, not on how it was spelled. The prompt tells it to type only what you asked for, as you gave it, never something of its own, and never from a scheduled message. The allowlist is the real guard; keep secrets out of the sessions on it.

Every machine has a name, and the name is the routing: `box_exec` goes to the one worker serving it. So a name belongs to one machine: the installer gives each an id of its own, and a second machine announcing a name already taken is refused: its worker waits and tries again hourly, its log says why, and it tells you once a day that a machine of that name is trying to join. A reinstall with the same hostname is the usual cause; "forget box" lets the new one in. Tell it what a machine is for ("the box is my dev server with the widgets checkout") and Fulla keeps it with the machine, so "run the tests on the dev server" finds it; "what machines do you know" lists them, and "forget the old box" drops one. With more than one connected it names the machine when it says what it ran, and asks when an ask could mean two.

A machine can also give it a shell of its own and its files: `FULLA_SHELL=1` in that machine's env file (the installer asks) turns on `<name>_exec`, which runs a command and returns its exit code and output, and `<name>_read_file`, `_write_file`, `_edit_file`, `_grep` and `_glob`, which touch files without a shell. Off, the tools are still in its list and refuse with a sentence saying so. On, everything runs as the worker's own user on your own machine, so it is your hands: Fulla is told to do what you asked for and what that plainly takes, to say what it ran when it matters, and to do nothing destructive you did not ask for by name. A command is killed past its timeout (120 seconds, 600 at most), output is capped, and the worker's Norns key is kept out of the command's environment. And only your word starts one: the worker asks Norns what started the run, and a command, a write or an edit on a run a timer started is refused, so its nightly review and check-ins can look at a machine but not change it. `mac_exec` on the Mac, `box_exec` on a box named box.

```bash
cp .env.host.example .env.host   # NORNS_URL, NORNS_API_KEY, FULLA_URL, FULLA_HOST, FULLA_TMUX_SESSIONS
uv run --env-file .env.host fulla-host   # try it in the foreground first
uv run fulla-host install        # then install it: asks for the values, enables the systemd user units
loginctl enable-linger $USER     # keep it up while you are logged out
```

`fulla-host install` asks for the five values (flags `--norns-url`, `--norns-api-key`, `--fulla-url`, `--host`, `--tmux-sessions`; an earlier install or `.env.host` is the default), writes them to `~/.config/fulla/host.env`, and writes and enables the units from `systemd/`: the worker, and the hourly update that pulls `main` and restarts it when it changed. The same merge-to-deploy as the Mac: keep the checkout on `main` with no local edits; `sh systemd/host-update.sh` is the update by hand after a merge.
