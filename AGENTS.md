# AGENTS.md

Guidance for agents working in this repository.

## What Fulla is

A private personal manager built on Norns. One Python process: a Norns worker serving eight fixed agent definitions (the manager, one reminder, one queued Mac task, one follow-up of Fulla's own, one watch on a coding sandbox, the web reader, the social agent for the owner's friends one to one, and one reminder for a friends' chat) plus one agent per allowed group, and a channel on Telegram, Signal, SMS, or any of them at once. Read `README.md` first, then `docs/architecture.md`; the rest of `docs/` is the owner's guide by topic.

## Layout

```

  main.py        entrypoints: `fulla-serve` (production, one process) and `fulla` (local dev)
  server.py      the one HTTP surface: /norns/wake, /norns/events, /telegram, /signal, /sms, /hosts, /egdir/hook, all authenticated
  signature.py   Norns's Stripe-style X-Norns-Signature, and the derived Telegram and Signal secrets
  wake.py        the worker as a serverless worker: incarnation loop, serve until idle, drain
  register.py    declares the worker to Norns from the agent definitions
  register_channel.py  creates the run webhook in Norns
  norns_api.py   the channel's own small REST client; the SDK would pull LiteLLM into a 256MB app
  config.py      config.yaml with ${VAR} / ${VAR:-default} interpolation; FULLA_REPO names its own repository, FULLA_COMMIT the commit it runs (baked in by CI)
  worker.py      the two Agent definitions and their prompts
  facts.py       FactStore, a JSON file: what the owner said about the world
  directives.py  DirectiveStore: how the owner wants Fulla to behave; rendered into the prompt
  soul.py        Soul: who Fulla is, a page in its own words (soul.md), rendered into the prompt; the `fulla-soul` CLI
  feedback.py    FeedbackStore: what the owner said it got wrong, resolved on the owner's word (`resolve_feedback`) or by `fulla-feedback`
  evals.py       `fulla-eval`: the manager's regression set against the real model; cases in evals/cases/*.yaml
  gaps.py        GapStore: what the owner asked for that it cannot do, with the nightly review's proposed fix and the commit that looks to have shipped it; closed on the owner's word (`resolve_gap`)
  limits.py      the hard limits: what code stops it doing, each naming its enforcement; rendered into the capability map
  review.py      the `fulla-feedback` CLI (runs on the Fly machine, where the file is)
  schedule.py    its timers: the owner's local times and days to the UTC cron Norns runs, and back for listing; the four scheduled turns' fixed messages
  calendar.py    read-only iCal feeds, recurrence expanded, cached ten minutes
  zones.py       a time said in another zone ("11am PT"): tools take `tz` and convert, the model never does
  transport.py   what the channel needs from a messenger: Inbound, and the Transport protocol both implement
  telegram.py    Bot API client: send, edit, answer_callback, long-poll; renders Markdown as Telegram HTML. Knows nothing about Norns.
  signal.py      signal-cli-rest-api client: the same surface, choices as a line to reply to; renders Markdown as Signal's styled text
  sms.py         Twilio client: the same surface over text messages; nothing for what a text cannot do; renders Markdown as plain GSM text, split into 1600-character messages
  channel.py     where the messenger and Norns meet. Fulla never imports this.
  confirm.py     confirm cards: a proposal the owner approves (Send/Edit/Cancel, as buttons or a reply line), pinned by digest, one-shot; `claim` for the machine that acts
  imessage.py    the iMessage kind of confirm card: render, edit, and Send starting the Mac delivery
  tools/         now, send_message (a message to the owner mid-turn, the manager's only), calendar*, remember/recall/forget, schedule_reminder/list_reminders/drop_reminder, list/set/drop_trigger (its timers in Norns), norns_run (one run by its id, owner-only), set/drop/list_directive, show/write_soul, note/list_feedback, note/list_gaps/propose_gap_fix, queue_for_mac/list_mac_queue, schedule/list/drop_followup, allow/drop_person, list_people, allow/drop_group, list_groups, set_group_tools, connect/disconnect_group_source, set_group_credential, draft_imessage, web_search/fetch_url (the reader's only); the groups' own, each bound to the run's group: group_sources, group_remember/group_recall, github_prs/pr/issues/issue/commits/file/search, linear_issues/issue, propose_merge/propose_issue/propose_review/propose_linear_issue (cards for the owner), linear_assign/update/comment/create_issue (at once, behind the owner's `linear_edit` switch), schedule_group_followup (a group's own check-back, behind `coding`)
  linear_cards.py the Linear kind of confirm card: a new issue, filed with the group's own key when the owner taps
  github_cards.py the GitHub kinds of confirm card: a merge of one exact head, a new issue, and a review (COMMENT, APPROVE or REQUEST_CHANGES) of one exact head, each done with the group's own token when the owner taps
  toolworker.py  the tools-only Norns worker both machine workers are built on
  tooldef.py     `norns.tool` re-exported with overloads, so the type checker reads `@tool(side_effect=True)` right; import `tool` from here
  tmux.py        the <host>_tmux_list/read/send tools, platform-neutral, allowlisted by session
  hosts.py       HostStore: the machines that have announced themselves (hosts.json), each with its own id (FULLA_MACHINE_ID) and what the owner said it is for; `announce`, and NameTaken when a name is another machine's
  people.py      PeopleStore: who else may talk to Fulla and in which groups (people.json); the owner's door
  groups.py      GroupStore: each allowed group's own directory (data/groups/<id>/): tools from the catalogue, sources, encrypted credentials, facts behind the screen, reminders
  injection.py   the screen in front of group memory: text that reads as instructions is refused (borrowed from Mimir)
  runctx.py      which run a tool serves, who spoke to it, and which chat it answers: the channel's knowledge, lent to tools
  groupctx.py    the inner lock: the group a tool serves, from the run; refuses outside the group's sources with fixed sentences
  coding.py      the inner lock on Bubbo's coding tools, which no tool of ours fronts: `CodingGuard` reads the model's calls in the worker's LLM path and holds a group to its own `github_repo` sources and its own sandboxes and jobs (`Sandboxes`, data/sandboxes.json)
norns_app/       what a Norns app shares, to be extracted when Mimir takes it too: github.py (REST), github_app.py (a GitHub App's installation tokens, minted per repository) and linear.py (GraphQL), clients over httpx with no allowlist of their own (scope is the caller's)
  untrusted.py   the marker around text written by someone other than the owner
  host.py        `fulla-host`: serves the tmux and shell tools from any non-Mac machine, under FULLA_HOST's name
  shell.py       the shell tools both machine workers serve under their prefix (`mac_exec`, `box_exec`, and read/write/edit_file, grep, glob), on only with FULLA_SHELL=1 on that machine, as the worker's own user, under a timeout and an output cap
  install.py     `fulla-mac install` and `fulla-host install`: the values to ~/.config/fulla/<kind>.env, the plists or units from launchd/ and systemd/, loaded; standard library only
  mac/           the Mac worker: `fulla-mac` (tools-only Norns worker) and the mac_* tools over osascript; the home is Shortcuts in one folder (`FULLA_MAC_HOME_FOLDER`)
launchd/         the plists that keep the Mac worker alive and updated; mac-python.sh, its own Python
systemd/         the user units that keep a host worker alive on Linux
deploy/signal/   the signal-cli machine: its Dockerfile, Fly config, run.py (the entrypoint; s6 cannot run under Fly's init), the forwarder that POSTs to /signal, register.sh
evals/           eval cases and the soul they run with; every fixed bug adds a case
tests/           pytest, no network: fakes for the messenger and the Norns client
```

## Rules

- Fulla is "it", never "she" or "he". That holds in prompts, tool descriptions, comments, docs, tests, commit messages and pull requests. Where "it" already means something else in the sentence, write "Fulla" or "the manager". Do not give it a gender or describe it as a person; pronouns for real people (the owner, friends) are unaffected.
- Fulla never acts in public. No tool may message anyone but the owner, with one exception: an iMessage the owner approved with Send on its card (a button on Telegram; on Signal a quoted reply "Send"; a reaction never sends), to a handle in the Mac's `FULLA_IMESSAGE_ALLOW` (empty by default). The manager may draft one on its own initiative (`draft_imessage`), but drafting sends nothing. Send is one-shot and pinned by digest: it starts a `fulla-mac-task` run whose `mac_imessage_deliver` claims the approved text from Fly (`/confirm/claim`) and sends exactly that, once. The manager never holds `mac_imessage_deliver`, and `mac_applescript` never addresses Messages, so no model call can send anything the owner did not approve.
- A confirm card is decided only by the owner, one to one, at the address the card was posted to. A button, quoted reply or reaction from anyone else, or from the owner in a group, never moves it; the card stores its address and the channel checks sender and chat, not just which message was quoted.
- Each allowed group has a directory of its own, `data/groups/<id>/` (`groups.py`), under a short id of Fulla's, since addresses change. `PeopleStore` stays the door; `GroupStore` holds what a group has: `group.json` (address, name, members, admin, `tools` from the fixed catalogue `groups.CATALOGUE`, `sources` in Mimir's shape, project, cap), `facts.json` (written only through `injection.scan`), `reminders.json` (that group's reminders; the shared `group_reminders.json` keeps a friend's one-to-one ones), and `credentials.json`, encrypted with `FULLA_SECRET`. The channel keeps the directories in step with the people store (`Channel._sync_groups`). Only the manager's tools write them (`list_groups`, `set_group_tools`, `connect_group_source`, `disconnect_group_source`, `set_group_credential`), so only the owner can, from their own chat. A credential goes in and never comes out: no tool reads one back, and `list_groups` says only which are set. With a GitHub App configured (`FULLA_GITHUB_APP_ID`, `FULLA_GITHUB_APP_KEY`) no GitHub token is stored at all: `GroupStore.github_token` mints an hour-long installation token for one repository, only for a repository among that group's sources at the moment of the call, kept in memory and never written; a stored GitHub token is then unused. Which group a tool serves comes from the run (`runctx.current_address`, lent by the channel from `social_origins`), never from an argument. The owner has a directory of the same shape, `data/groups/owner/` (`GroupStore.owner`, named "me" to the tools, left out of `all()` so it gets no agent): the manager holds the same `github_` and `linear_` tools over it, and `groupctx.current` resolves it only when the calling run is the manager's by the agent id core put on the task (`runctx.current_is_manager`, answered by the worker from the server's definitions), never from a model argument; a group's run is its group's or nothing. The group tools (`tools/group_github.py`, `tools/group_linear.py`, `tools/group_memory.py`) are the catalogue's entries made real: each takes its group from `groupctx`, its token from that group's credentials and its repositories from that group's sources, wraps what strangers wrote in the untrusted marker, and answers every failure with a fixed sentence. A GitHub write, and a Linear filing by default, is never done by a tool: `propose_merge`, `propose_issue`, `propose_review` and `propose_linear_issue` post a card to the owner's own chat (`github_cards.py`, `linear_cards.py`), and the owner's tap acts with the group's token or key, the merge and the review pinned to the head the card showed. The one write a group may do at once is behind the owner's `linear_edit` entry in the catalogue (it switches `linear` on too): `linear_assign`, `linear_update` (state, priority, title, labels), `linear_comment` and `linear_create_issue`, with the group's own key, on issues in the group's own teams and projects, names resolved against Linear (an assignee, a state, a label) and never taken as ids, nothing deleted or archived; the manager holds them always, over the owner's own directory. The allowlist keeps them off a group without the switch, and the tool refuses from inside too (`group_linear._editable`). A Linear issue a key can reach but the group's teams and projects do not hold is refused after the fetch, the same sentence as before it, on a write as on a read. The social agent serves every group tool so each incarnation can answer them and the declaration lists them, but is allowed only the social set: the allowlist is the wall, the served set is plumbing. The owner's `coding` entry puts the Bubbo worker's coding tools (`coding.CODING_TOOLS`, served by Bubbo, never by Fulla) on that group's allowlist, after construction as the manager's are, with `schedule_group_followup`, a check-back that rides the group-reminder carrier and comes back into the group's own conversation (`Channel._relay_group_reminder`, counted against the day's cap) instead of being posted. Since no Fulla tool sits in front of Bubbo's, the inner lock is in the worker's LLM path: `wake.ServingNorns` hands every response of the manager and the group agents to `coding.CodingGuard.check`, which takes the scope from the agent id core put on the task, lets a group provision only a repository among its own `github_repo` sources (named by identifier or label, sent as the identifier) and drive only the sandboxes and jobs its own provisions and starts created (claimed from the tool results in its own history, first claim wins), keeps the manager off any group's, and refuses everything for any other agent; a refusal replaces the step with a fixed sentence as the run's answer. Anyone in the group may use them, and `open_pull_request` opens a draft at once, with no card.
- The one door the owner can open is `people.json` (`people.py`): people they list, and groups they allow after Fulla asks them privately. Anyone else, anywhere else, is dropped by the channel. A listed person one to one gets `fulla-social`, and anyone listed speaking in an allowed group (the owner included) gets that group's own agent, `fulla-group-<id>` (`worker.group_agent`, built from the group's directory at every join and pushed over REST when the owner changes the group or allows it, `main.push_groups`; the channel answers through `fulla-social` only while a group's agent is not on the server yet), never the manager: its own conversation per address (`social:<address>`), a tool list of `now`, `group_sources`, the reader when the owner enabled the web for that group, what else the owner enabled from the catalogue (`tools.GROUP_TOOL_SETS`), and reminders that post back into that chat (`schedule_group_reminder`, a run of `fulla-group-reminder` indexed against the run that set it, found by `runctx.current_run_id`, tagging the asker found by `runctx.current_speakers`, or the group member the ask names, found in `PeopleStore.members` through `runctx.current_address`: in both cases the channel's record of who has spoken in that chat, never a model-supplied identity), no facts, calendar, the owner's reminders, machines, directives or soul, in the prompt or behind a tool. The wall is the tool list; a prompt rule is not a lock. That wall is two locks per group: Norns's allowlist on the group's agent (outer), and the tool itself resolving its group from the run through `groupctx` (inner), refusing with a fixed sentence when there is no group and refusing any repository, team or host outside the group's sources even when the model names one; with none named it works on the group's own, never "all". The group is never a tool argument, a group prompt names no other group and nothing of the owner's or of Fulla's own (no file, host, model or key), and a tool's error to a group is a fixed sentence, never an exception, path or URL. The social and group agents never sleep: `wait` is withheld from them (`wake.WITHHELD`, `wake.withheld_for` by name prefix for the group agents), since a sleeping run would hold the chat busy and queue everyone behind it, and if one sleeps anyway the channel cancels it when the next message arrives. Their words reach it inside the untrusted marker. So does the thread: the channel keeps each allowed group's last few messages (`ChannelState.group_ring`, `channel.group_context` of them, two hours at most, Fulla's own posts included) and prepends them, as one untrusted block, to a message that addresses it; the social agent has no tool to read a chat, the channel decides what it sees. Everyone who speaks in an allowed group is recorded as a member of it (`PeopleStore.saw_in_group`); a `Person` has an id of Fulla's own, and a `Group` lists its members by it. A mention goes out as `mentions` on `Transport.send`, over an "@<name>" the channel wrote; the model never produces one. In a group Fulla answers only when addressed by name, by its bot handle, or by a reply to it, and each conversation has a daily cap (`channel.social_daily_cap`). Only the manager's tools change the lists, so only the owner can.
- The Mac worker serves tools and nothing else. It never defines an agent, never serves an LLM call, and the Fly worker never serves or declares a `mac_*` tool. The manager allowlists them; Norns offers them while the Mac is connected. Adding a Mac tool means adding it to `mac_tools`; no re-registration.
- The Mac worker runs on its own Python (`launchd/mac-python.sh`, under `~/Library/Application Support/Fulla`), started by launchd directly, never through uv. macOS permissions are granted to that binary only; nothing may tell the owner to grant uv or uv's shared Python.
- AppleScript is allowlisted by app (`FULLA_MAC_APPS`) and refused when it shells out, builds a script from text, or names an app indirectly. This is a filter on script text, not a sandbox: keep the app list short. Owner data goes to osascript as argv, never spliced into script text.
- Fulla runs commands only on the owner's own machines, as the owner allowed on each: by typing into sessions named in `FULLA_TMUX_SESSIONS` (empty by default; the check is on the session tmux resolves the target to, and text and targets go to tmux as argv, never through a shell), and with `<name>_exec` and the file tools (`shell.py`) where the owner set `FULLA_SHELL=1` in that machine's env file. The shell tools are served and allowlisted on every machine and refuse while the switch is off, like tmux without sessions; on, they run as the worker's own user, under a timeout (the process group killed past it) and an output cap, with the Norns key out of the command's environment. Each machine serves both under its own prefix (`mac_`, or `FULLA_HOST` for `fulla-host`), and the announcement to `/hosts` says whether its shell is on. The prompt tells the manager a shell is the owner's hands: what they asked for and what that plainly takes, nothing destructive unasked. The lock under it is the run's origin: `exec`, `write_file` and `edit_file` refuse unless Norns says the run was started by a message (`shell.owner_started` over `shell.run_origin`, which asks Norns by the run id core put on the task and remembers the answer per run; nothing known means refuse), so a scheduled turn can read a machine and change nothing, and `fulla-mac-task` holds no shell tool, since a queued task is a run of its own started by a message.
- Machines are not configured on Fly. A worker announces itself to `/hosts` on start; `HostStore` remembers it, and the manager's allowlist, Machines section and per-turn note are all built from the store. A new machine is a worker that started once, not new code. The name is the routing (Norns dispatches `box_exec` to the worker serving it), so a name belongs to one machine: the installer writes a `FULLA_MACHINE_ID` and the worker announces it, `/hosts` refuses the name from another id with 409, and the worker waits an hour and tries again instead of serving a coin toss (`announce_until_named`; an exit would only have the supervisor restart it every ten seconds, waking the Fly app each time), while Fulla tells the owner once a day in chat (`Channel.tell_owner`, `Refusals`) that a machine of that name is trying to join and how to let it in. What a machine is for is the owner's word, kept in the store (`describe_machine`) and rendered into the Machines section; `forget_machine` drops one; neither is ever set from an announcement. The prompt has the manager name the machine when more than one is connected, and ask rather than pick when an ask could mean two.
- A turn's final reply is one message; the manager sends more with `send_message` (`tools/messages.py`), delivered at once by `Channel.say` the way the final reply is (to where the run answers, deduped by run and text). It is the manager's alone, and the tool refuses unless `runctx.current_is_manager`. A final `[silent]` drops only the final reply. The nightly review and the shipping check, which are never delivered, are not offered it (`wake.WITHHELD_ON_QUIET`); the other scheduled turns keep it.
- The manager never sleeps. Anything with a due time becomes a reminder run via `schedule_reminder`, or a follow-up run via `schedule_followup` when it is Fulla's own check-back, never `wait` in the manager; `wake.WITHHELD` takes `wait` out of its calls. A follow-up run is never relayed; it reaches the owner only through the manager's `[scheduled] follow-up` turn.
- The manager never polls. Every turn of the manager's resends its whole prompt and tool list, so a check that is usually "still running" belongs to a small agent: a coding sandbox is watched by `fulla-watch` (`watch_environment`), which polls Bubbo's two read tools on the light model and delivers one follow-up when the state changes, carrying nothing from the tool output but the state reduced to two words (`followups._state`). `coding.CodingGuard` holds the watcher to those reads on what the manager may drive. Only the manager runs on `fulla.model`; the reader, the Mac queue, friends and groups run on `fulla.mid_model`, and the timers (reminders, follow-ups, the watcher) on `fulla.light_model` (`worker.mid_model`, `worker.light_model`).
- The manager never waits for the Mac either. A Mac task asked for while the `mac_*` tools are absent becomes a run of `fulla-mac-task` via `queue_for_mac`; that run parks on `ask_human` ("Waiting for the Mac."), which the Mac worker answers on every successful join (`fulla/mac/nudge.py`). Nothing polls. The channel never posts that question, and relays the run's output only if `data/mac_queue.json` knows it, like reminders.
- The channel is the only module that knows about the messengers, and it knows them only as `transport.Transport`s, by name, any number at once. It speaks of addresses (`telegram:<chat>`, `signal:<number>`) and names a message by address and id together; every run remembers the address it came from and is answered there, and what has no origin (a scheduled turn, a reminder) goes to the primary address, `channel.primary`. Agent prompts and tools stay channel-blind. A transport knows nothing about Norns.
- The standing conversation's key is `config.conversation_key`, built there and nowhere else; the channel chats in it and the follow-up tool writes into it. The triggers are Fulla's own: `set_trigger` makes and moves them in Norns with the key it holds, always on the manager and this conversation (fixed at init, never an argument), from times in the owner's zone, and only on the owner's word. Nothing at start or in CI creates, moves or removes a trigger; `nornsctl triggers list` is the truth, and a trigger made by hand is one it lists and can change. Switching messenger means setting each again, which re-points it (`docs/messengers.md`, "Signal").
- signal-cli runs on its own always-on Fly machine (`deploy/signal/`), never in the Fulla app, which sleeps. Fulla never holds its receive stream in production: the forwarder beside signal-cli spools each envelope to the volume and POSTs it to `/signal`, signed with a secret derived from the webhook's, retrying in order until Fulla answers (Signal delivers once; nothing may be dropped), and the server drops everyone but the owner. An owner message counts as handled only once Norns has it or it is kept in `pending`; if Norns is unreachable, `channel.handle` raises `NotTaken` and the server answers 503 so the messenger brings it again. A message already handled is ignored, so a retry is safe. Signal has no buttons (`Transport.buttons`): the channel's choices go out as a line to reply to and a quoted reply or a reaction answers; work shows as the typing indicator alone, with no Working… message; and a message that is only "wait", "cancel", "stop", "nvm" or the like while a run is in flight cancels it, on either messenger.
- SMS is Twilio's webhook into `/sms`, signed with the account's auth token over the URL and the fields; the fallback URL is the same route, since Twilio never retries on its own. A text cannot be edited, deleted, quoted or reacted to, and the transport does nothing for those; the channel does not branch on the messenger. The one accommodation is shared with Signal: on a messenger without buttons, an unquoted message that is exactly a label of an open question or the one open card is that button. SMS carries the owner's chat only; the number's webhook is owner-filtered by the channel like every other inbound.
- The channel never imports `norns`. It uses `norns_api.py`. Adding a tool to a Fly-served agent means re-declaring the serverless worker; CI does that on merge (`fulla-register`, idempotent).
- Nothing is posted twice. The channel persists what it has posted and relayed, and which runs it is showing as working, in `data/channel.json`; keep that true when you change it. Norns may deliver an event twice and reconcile may see a question already delivered.
- The channel never polls. Outbound comes from run webhook events; the only list call is `reconcile()` on a cold start.
- Facts are the owner's words. Store what they said, not a summary.
- The manager's system prompt is `worker.manager_prompt(config, directives, hosts, soul)`, rendered in two places: when the worker joins (built fresh for each incarnation, since the SDK upserts the definition on every join) and when the soul or a directive changes or a machine announces itself (pushed over REST, with the allowlist). Never build it a third way.
- Fulla never claims or offers a capability that is not in its tool list or on its capability map, `worker.capability_map`, rendered into the manager's prompt from `SUBAGENTS`, `HostStore`, the machine and coding tool lists and `limits.py`; nobody writes it by hand. Its own tools are in its list on every turn, so the map does not name them again: it holds what the list cannot show. A hard limit goes in `limits.py` only when code enforces it, naming that code. Asked for something off the map, it says so and calls `note_gap`, only from the owner's own words, never from iMessage, web or other untrusted text; `fulla-social` holds no gap tool, so a friend or group never makes one. The nightly review proposes a fix for each gap and never starts one. A gap or a feedback item closes only on the owner's own word in their chat (`resolve_gap`, `resolve_feedback`) or by `fulla-feedback` on the machine. With `FULLA_REPO` set and that repository among the owner's sources, the prompt names it as its own code with the running commit, and a scheduled `[scheduled] shipping check` turn of its own (not the nightly review, whose step budget goes to memory) reads its recent commits and notes which gaps and feedback items one appears to address (`note_gap_shipped`, `note_feedback_shipped`, five a night at most); the morning brief asks the owner. A note is never a close, and what it reads of its own code is untrusted text that changes nothing about it.
- The soul is Fulla's voice, not a rule and not a fact: a page of first-person prose in `soul.md`, written with the owner on first contact and revised by the owner's ask or one line a night by the nightly review. Directives are rules about what to do; the prompt tells the manager which is which. Only `write_soul` and `fulla-soul` write the file. The per-call additions are two, both appended by `wake.with_turn_note`: `worker.turn_note`, from the tool list core sent, a statement of fact (which `mac_` tools are present this turn), because the model will not read the tool list over its own history; and, on a turn a timer started, `worker.scheduled_playbook`: the rules every scheduled turn follows and that turn's own instructions (`worker.PLAYBOOKS`, one per entry in `schedule.TURNS`). What a scheduled turn does lives there and never in the standing prompt, so an ordinary turn does not carry it. The standing prompt is held to a budget (`tests/test_turn_tools.py`). New guidance goes where it costs least: a lock in code, then the tool's own description, then a scheduled turn's playbook, and into the standing prompt only when it is judgment across tools.
- A scheduled turn of the manager's is offered fewer tools (`wake.offered`). No machine's typing tools (`wake.TYPING`: `<name>_tmux_send`, `_tmux_new`, `_tmux_rename`) on any turn a timer started, a follow-up and the owner's own timers included. And each of the five scheduled turns only its own set, `worker.TURN_TOOLS`: the brief and the check-in look (the reading tools, each machine's among them, and what the owner's standing instructions have them read) and do not touch; the nightly review, the shipping check and the question hold what their playbooks name. A turn starts cold, so every definition it carries is paid for in full. A tool a playbook names must be in that turn's set, and a test holds the two together. The turn note is told what core sent, so a machine whose tools a turn does not carry is not called off. A message of the owner's that joins a scheduled run makes the rest of it their turn, with every tool.
- The channel's `/reset` deletes the standing conversation, and `/reset <group or person>` a social one (`social:<address>`, with the run in flight there, what is queued behind it, and the group's thread; the people list, their reminders and the day's count stay). Both are the owner's escape hatch when the window itself has become the bug, taken only in the owner's own chat; nothing else deletes conversations.
- A run that reads the web holds no side-effecting tool. `web_search` and `fetch_url` belong to `fulla-reader` alone, never to the manager's allowlist; the manager reaches the reader through `launch_agent` (its only allowed sub-agent) and gets back an answer, not pages. `fetch_url` fetches only public addresses, re-checked on every redirect.
- A scheduled run never calls `ask_human`. Parking the standing conversation would swallow the owner's next message as the answer. Scheduled runs suggest in text or end with `[silent]`. Two locks hold it: the worker does not offer `ask_human` on a turn whose message begins `[scheduled]` (`wake.WITHHELD_ON_SCHEDULED`), and the channel answers a timer-started manager run that asks anyway instead of posting its question (`Channel._on_a_timer`).

## Commands

```bash
uv sync
uv run pytest
uv run ruff check .
uv run pyright
uv run --env-file .env fulla-eval   # the manager's evals; needs ANTHROPIC_API_KEY
uv run fulla            # local dev, with a dev bot token
uv run --env-file .env.mac fulla-mac   # the Mac worker, in the foreground
uv run fulla-mac install               # install it under launchd (fulla-host install on a Linux box)
```

Work in a git worktree on a branch and land it through a pull request; never commit on `main`. CI (`.github/workflows/ci.yml`) runs ruff, pyright and pytest on every PR, and a merge to `main` deploys to Fly from the committed tree. Do not `fly deploy` from a working copy.

Norns must be reachable at `NORNS_URL`. Use `nornsctl runs list` and `nornsctl runs events <id>` to see what the runtime did.
